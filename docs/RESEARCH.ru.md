# Исследование Lighter / Robinhood Chain

Проверено 20 октября 2026 года реальными HTTP/WebSocket-запросами и по первичным источникам. В проекте изначально был только `bot.png`; затем добавлен второй образец. Исходный код и доступ к оригинальному боту отсутствуют.

## Можно ли узнавать Premium

Публичная лента исполненных сделок содержит ставки обеих сторон. В текущем тарифе RH Premium и Plus имеют непересекающиеся комиссии, а Standard имеет нулевые ставки и 100 ticks для taker TWAP. Поэтому можно классифицировать стороны **в момент сделки по тарифу**. Это не прямое доказательство приватного флага и не список всех Premium-аккаунтов, включая не торгующих.

Прямые пробы `accountLimits?account_index=…` и `l1Metadata?l1_address=…` без токена вернули 400 с требованием `auth`/`Authorization`. Обычный `account` доступен, но `account_type` не является тарифным признаком Standard/Premium. Приватные endpoints не нужны реализации.

| Тариф | maker_fee, ticks | taker_fee, ticks |
| --- | --- | --- |
| Standard | 0 | 0; TWAP — 100 |
| Plus | 150 | 150 |
| Premium, уровни объёма | 120, 117, 114, 108, 102, 96, 84 | 350, 341, 333, 315, 298, 280, 245 |

В этих полях 120 ticks соответствует 0.0120%. Не путать ticks со списанным долларовым размером комиссии. Положительная комиссия сама по себе недостаточна для признания Premium. Отсутствующее поле нулевой комиссии означает 0 по протоколу, а явный null/некорректный тип — unknown. Ставки не экстраполируются на будущее; кэш «этот аккаунт Premium навсегда» не используется.

В живом потоке OPENAI реально наблюдались, например, `maker_fee=0, taker_fee=280` и `maker_fee=0, taker_fee=100`: первая сделка Standard/Premium, вторая Standard/Standard с TWAP taker. В расширенном тесте встречались также Plus. Обезличенные технические примеры есть в JSON-отчёте (только публичные account index, без кошельков/ключей).

## RWA

Используются **две** публичные выборки: `orderBooks` даёт активные рынки и их ID, `tokenlist` — `asset_type` и `categories`. Выборка по умолчанию требует `asset_type=RWA`, любую из категорий `STOCK,PRE_IPO` и тип рынка `perp`. Динамический ID берётся из ответа, не угадывается по диапазону. Криптовалюта с похожим тикером/категорией пройти этот фильтр не может.

На дату проверки: AAPL, AMC, AMD, AMZN, ANTHROPIC, ASTS, BABA, BE, CLSK, COIN, CRCL, CRWV, GOOGL, INTC, IREN, LUNR, META, MSFT, MU, NVDA, OPENAI, ORCL, PLTR, QBTS, RGTI, SHEIN, SKHY, SMCI, SNDK, SOFI, SPCX, TSLA, TSM, WULF.

QQQ/SPY и металлы из второго снимка входят в RWA, но имеют категории ETF/COMMODITIES. Их можно включить, очистив `RWA_CATEGORIES`. В данной поставке по уточнению пользователя включены акции/pre-IPO. Классификация venue сохраняется: бот не определяет актуальный юридический статус IPO компании.

## Аналитика и трактовка изображений

В первом снимке `982 + 385586 + 7086 = 393654`: Premium-объём — сумма сделок с хотя бы одной Premium-стороной без удвоения Premium/Premium. Доля — Premium-объём / весь объём. Округлённые 100% на изображении соответствуют 99.65% до округления. Эти свойства воспроизведены.

Для времени t, окна W секунд и среднего периода B:

```text
current = fills с t-W < timestamp <= t
premium_per_minute = сумма usd_amount Premium в current × 60/W
baseline = сумма Premium в предшествующем наблюдаемом интервале / число минут
ratio = premium_per_minute / max(baseline, BASELINE_FLOOR_USD)
```

Среднее исключает текущее окно и включает наблюдаемые минуты без сделок. Требуются непрерывный прогрев и все настроенные пороги. Итоги в leaderboard делятся на полный выбранный период; если он ещё не накоплен, интерфейс явно сообщает об этом.

Семантика стрелок и кнопок не установима только по изображениям. Реализация выбирает maker→taker, позволяет переключить на продавец→покупатель; кнопки тикеров управляют уведомлениями. Исходные пороги и формула среднего неизвестны. Их точное совпадение с оригиналом не заявляется.

## Надёжность

Данные поступают через публичный `wss://api.rh.lighter.xyz/stream?readonly=true`. Ручной JSON ping каждые 30 секунд дополняет обработку ping сервера. Это необходимо: обычный heartbeat aiohttp откладывается на активном входящем потоке. В первоначальной живой проверке сервер закрывал соединение примерно через 2 минуты 16 секунд; найдено и исправлено отдельным таймером исходящего ping.

Исторические сделки в `subscribed/trade` не выдаются за полный backfill. Ликвидации из отдельного массива не считаются обычной торговлей. После переподключения прогрев начинается заново. `trade_id_str` хранится строкой; SQLite обеспечивает уникальность `(market_id, trade_id)` и атомарную запись сигнала с очередью доставки.

Запросы аккаунтов на каждую сделку отсутствуют. REST используется для метаданных раз в 15 минут. Подписки отправляются с интервалом 0.4с; heartbeat и ответы укладываются в опубликованный бюджет. Обработка `shutdown`, backoff, сохранение настроек/сигналов, авторизация команд и срок годности доставки реализованы.
